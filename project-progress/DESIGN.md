# 项目进度管理 · 设计记录（实际成品）

seed 2fc4dc8e · grounded direction rank 1 · 工程总控墙

本文件描述 `project-progress/` 当前实际实现的视觉与信息系统，而非设计意图。
验收截图（provenance）：`.impeccable/review/project-progress/desktop.png`（1440×1100 首屏）、`.impeccable/review/project-progress/entry.png`（原型入口第三按钮）。

## 定位

面向甲方阅读的桌面大屏"工程总控墙"：把开发工作量、相对周排期、人工进度和会阻塞研发的甲方前置事项放在同一视野。不是内部项目管理工具，不做编辑、筛选、搜索、移动适配、打印或 PDF。

## 视觉系统（成品）

- **底色**：冷灰墙面 `#f4f5f6`，面板 `#fbfcfc`。无渐变、无玻璃、无阴影堆叠、无 hero。
- **线条**：石墨细线承担全部结构。面板外框 `1px #3a424a`，分隔线 `1px #c9ced3`。总控板周格线 1px，缓冲区周格线为虚线。
- **颜色纪律**：
  - 低饱和绿（填充 `#79a188`、文字 `#4e7a5e`）只表示研发进度与已完成状态。
  - 琥珀（文字 `#9a670e` / `#7d5208`、底 `#f6ecd9`）只用于当前适用且未完成的待甲方预备事项：顶部提醒条带、待甲方预备泳道图钉与文字、清单中的"未完成"状态签。研发区域不出现琥珀。
  - 条件待确认（`active=false`）使用中性石墨虚线，不计入当前欠缺，不使用琥珀。
  - 状态不只靠颜色：进行中=绿色填充比例，已完成=实心绿+文字"已完成"，未开始=石墨描边，等待外部条件=虚线描边+文字"等待外部条件"，缓冲区=虚线区+标尺"20% 缓冲"标注，条件待确认=虚线图钉+虚线状态签。
- **字体**：系统中文字体栈（PingFang SC / Hiragino Sans GB / Microsoft YaHei / Noto Sans CJK SC），数字统一 `font-variant-numeric: tabular-nums`。无外部字体、无图标字体、无 emoji / Unicode 图标（图钉、箭头均为 CSS 绘制）。
- **动效**：仅任务明细展开/收起一处过渡（grid-template-rows 240ms），`prefers-reduced-motion` 下全部关闭。内容默认可见，无入场动画。
- **可访问性**：展开/收起为语义化 `<button>` 并同步 `aria-expanded`；`:focus-visible` 绿色 2px 焦点环；自定义选择色（石墨底白字）与细滚动条；正文对比度 ≥ 4.5:1。

## 版面结构（自上而下）

1. **顶栏**：标题"项目进度管理"、中部**项目开始日期**控制区（原生 `input type=date` + **每周工作日**单选组：5 天周一至周五 / 6 天周一至周六）、最后更新时间（HEAD 请求 `data.js` 的 `Last-Modified`，失败回退 `document.lastModified`，中文格式化）、返回原型入口链接。顶栏三列网格：左标题、中日期控制、右元信息；1440px 视口内不溢出。日期控制区第一行为「项目开始日期」输入与派生「研发计划完成」「含缓冲完成」（未设定时显示「待选择」）；第二行为工作周单选（原生 `radio`，`accent-color` 绿色，标签可点击）；第三行为由脚本写入的工作日推算说明（`date-hint`）；若所选日为当前口径下的非工作日，输入保留原值并显示顺延起算提示（5 天制周六顺延、6 天制周六不顺延）。
2. **总控数据带**：一条带细分隔线的连续数据板——基础工作量 49 人日 / 392 人时 / 人力缓冲 9.8 人日 / 78.4 人时（20%）/ 合计 58.8 人日 / 470.4 人时 / 总体进度（附绿色进度轨）/ 进行中任务 / 待甲方预备（仅统计 `active=true` 且未完成，初始 10 项；副文案注明另有 4 项条件待确认）。工作量三格在同一数值区同时显示人日与人时；数字全部由 `data.js` 实时计算。
3. **待甲方预备条带**：琥珀底细边条，按四类（账号与资质 / 技术资源 / 合规发布 / 微信支付）汇总当前未完成数量，并单独说明条件待确认数量；全部完成时转为绿色提示。
4. **周次排期总控板**：第 1–11 周标尺（第 10–11 周为虚线 20% 缓冲区）；**有项目开始日期时**每格在「第 N 周」下显示紧凑 `M/D–M/D` 区间，完整区间放 `title`/`aria-label`，缓冲周仍保留「20% 缓冲」标注。左侧 360px 固定信息列（sticky，`z-index: 3`，背景与右边框遮住横滑周轨），周列固定 100px，整板约 1460px（360 + 11×100），超出 1360px 页面容器时仅 `.schedule-scroll` 内横向滚动，页面 body 无横向溢出。滚动提示「左侧任务固定，横向滑动查看第 1–11 周」位于板上方；滚动容器 `tabindex=0` 与 `aria-label` 支持键盘聚焦。泳道头部左列为两层：完整 lane-name（禁止收缩与逐字换行）+ lane-meta（可自然换行但不拆单字）。研发任务左列标题 + 元信息两层（不额外塞日期；计划完成由标尺与任务条表达）；元信息中分组标签独立不压扁，详情文字包在 `task-meta-detail` 内尾部省略。任务条 `title`/`aria-label` 在有日期时追加计划完成日。待甲方预备行左列为三层：`task-name` 事项标题、`prereq-owner-role` 责任方（统一显示「甲方」，360px 内自然换行，禁止省略号与逐字断行）、`prereq-week-status` 期望周次、最迟完成日与状态；行高随三层内容自然增高；右侧图钉标签有日期时显示 `状态 · M/D`。五条工作线：产品（1 行）、前端（21 行）、后端（10 行）、部署（6 行）、待甲方预备（14 行里程碑图钉）。`script.js` 从根 `--week-w` 读取周列宽（回退 100px）计算任务条与图钉位置。板下注明 H5 兜底策略与支付承接边界。
5. **任务明细**：按状态分组（进行中、等待外部条件默认展开；未开始、已完成默认收起），表格仅含任务、预计人日 / 人时（单栏双单位）、人工进度三列；任务 meta 在有开始日期时于周次后追加「计划完成 M月D日」。
6. **待甲方预备完整清单**：5 列（待甲方预备事项 / 责任方 / 期望周次 / 状态 / 受影响任务）。责任方统一显示「甲方」。期望周次列保持一列：上行「第 N 周」、有日期时下行「最迟 M月D日」。第一列在标题下紧凑展示分类、必需程度或适用条件、可核验完成标准、官方依据外链（新窗口 + noopener）。状态列：`active=false` 显示"条件待确认"，`active=true` 显示未完成/已完成。
7. **范围待确认**：5 项编号列表，仅展示不统计，注明"确认后重新评估并更新当前计划"。
8. **排期说明页脚**：人员配置、前后端并行与 Mock、当前工作周（5 或 6 日）与 8 小时/人日、20% 缓冲独立计算、范围待确认不统计、支付承接边界说明；有开始日期时追加 URL 规则（含 `workdays=5|6`）、工作日算法与各节点日期映射说明。

## 数据与计算

- 唯一数据源 `data.js`：38 条研发任务（49 人日 / 392 人时：产品设计 2 / PC 管理端 18 / 小程序 8 / 后端 16 / 部署 5）、14 条待甲方预备事项（账号与资质 5 / 技术资源 3 / 合规发布 2 / 微信支付 4）、5 条范围待确认。
- 待甲方预备：`active=true` 表示当前适用（初始 10 条）；`active=false` 为条件项（初始 4 条：微信认证、商户号与支付权限、AppID 绑定与安全参数、支付回调与真实支付退款闭环）。条件成立时维护者改 `active=true` 再更新 `status`。
- 顶部「待甲方预备」只统计 `active=true` 且 `status≠complete`；条件项不计入欠缺。
- 责任方统一为「甲方」，不展示细分角色。
- 缓冲率 20% 单独计算（49 × 20% = 9.8 人日 / 78.4 人时，第 10–11 周虚线区），不摊入任何任务；含缓冲合计 58.8 人日 / 470.4 人时。
- 人时由 `workdays × meta.hoursPerWorkday` 派生；`script.js` 集中格式化，不在 HTML 或页面逻辑中硬编码汇总数字。
- 分类与总体进度均为研发任务 `progress` 的简单平均；`progress = 100` 自动视为已完成；前置事项与范围待确认不参与任何统计。
- 维护方式：只改 `data.js` 中任务的 `progress / status / startWeek / endWeek`；前置事项的 `status / expectedWeek / active`（条件成立时）；可选 `meta.projectStartDate` 设定默认开始日期。

## 项目开始日期与工作日换算

- **数据字段**：`meta.projectStartDate`（`YYYY-MM-DD` 字符串，可选，空表示未设定）；`meta.workdaysPerWeek`（发布默认值 `5`，仅允许 `5` 或 `6`）；`meta.planWorkdaysPerWeek`（每个计划周固定承载的基准工作日数，固定 `5`，不随顶栏 5/6 天单选变化）。
- **URL 规则**：`?start=YYYY-MM-DD` 优先级高于 `meta.projectStartDate`；`?workdays=5|6` 优先级高于 `meta.workdaysPerWeek`，无效值回退 `5`。有效日期或工作周变更后通过 `history.replaceState` 同步 URL（保留其他参数）；清空开始日期时仅移除 `start`，保留 `workdays`。不使用 `localStorage`。
- **解析顺序**：初次加载先解析工作周口径，再解析开始日期。严格本地日期解析 `YYYY-MM-DD`（`new Date(y, m-1, d)`），避免 UTC 偏移。
- **非工作日顺延**：所选日期若为当前口径下的非工作日，输入框保留用户所选日期，有效排期起算日顺延至下一工作日；顶栏显示顺延说明。5 天制：周六、周日为非工作日（例：`2026-09-05` 周六顺延至 9 月 7 日）；6 天制：仅周日为非工作日（同例周六从 9 月 5 日起算、无顺延提示）。
- **工作日算法**：计划周基准工作量固定为 `meta.planWorkdaysPerWeek`（5 个基准工作日/计划周），与顶栏 5/6 天单选无关。第 N 周开始 = 有效起算日后 (N−1)×`planWorkdaysPerWeek` 个工作日；第 N 周结束 = 有效起算日后 N×`planWorkdaysPerWeek`−1 个工作日。`getWorkdayAt` 根据 `dateCtx.workdaysPerWeek` 决定哪些日历日可工作：5 天制跳过周六、周日，6 天制仅跳过周日。5/6 天选项只改变日历产能，不改变任务工作量；6 天制下相同基准工作日更快消化，完成节点相应提前。6 天制下计划周日期块可跨自然周（例：`start=2026-09-07` 时第 1 周 9/7–9/11、第 2 周 9/12–9/17）。不识别法定节假日。
- **修复案例**：此前第 N 周偏移误乘 `dateCtx.workdaysPerWeek`，导致 6 天制把每计划周工作量从 5 扩到 6、完成日反而晚于 5 天制（`start=2026-09-07` 时研发完成 11/7 > 11/6）。修复后偏移固定乘 `planWorkdaysPerWeek`；`workdays=5` 研发完成 11/6、含缓冲 11/20；`workdays=6` 研发完成 10/28、含缓冲 11/9。
- **动态重算**：切换 5/6 天或变更开始日期时，标尺周区间、任务/甲方节点日期、顶栏派生日期与页脚说明原地重渲染，不刷新页面；任务 `startWeek`/`endWeek`/`expectedWeek` 数据不变。
- **节点映射**：任务计划完成 = `endWeek` 周结束日；甲方最迟完成 = `expectedWeek` 周结束日；研发计划完成 = `devEndWeek`（9）周结束日；含缓冲完成 = `totalWeeks`（11）周结束日。
- **无日期回退**：无 URL 参数且 `projectStartDate` 为空时，页面保持相对周次展示（标尺仅「第 N 周」、派生日期显示「待选择」），工作周单选与 `date-hint` 仍按当前口径正确显示。
- **局部重渲染**：日期或工作周变更仅重渲染排期板、任务明细、甲方清单、页脚说明与顶栏日期摘要；总控数据带与琥珀条带不重绘。
- **显示格式**：顶栏派生日期用 `YYYY年M月D日`；周格与图钉用 `M/D`；正文节点用 `M月D日`；跨年时 `title`/`aria-label` 含完整年份。

## 支付边界（页面明示）

- 报告模块只跳转现有商城，不处理订单支付（见业务设计）。
- 若支付由独立商城小程序承接，报告小程序不需要新的商户号或支付密钥。
- 若当前 AppID 直接支付，才需商户权限、AppID 绑定、安全参数、HTTPS 回调和真实支付退款闭环，并需重新评估研发范围。

## 已知取舍

- 周列固定像素（100px）、左列 360px；1440px 及以下宽视口由总控板内部横向滚动承接，左列 sticky 保持可读；不缩小字体或压缩周列，不做移动端响应式重排。
- 不绘制任务依赖箭头（`dependencyIds` 仅存于数据），不计算或推演延期。
- 初始总体进度 3%（仅"产品设计"100%），属真实初始状态而非占位美化。
- 研究详情不整段塞进总控页，详细办理材料见 `docs/product-design/wechat-mini-program-client-preparation-research.md`。
