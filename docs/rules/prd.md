# PRD 写法

## 一轮需求一篇

每轮需求使用 `docs/requirements/<稳定专题名>/README.md`。一篇 PRD 可以同时描述不同端的同一轮改动。新一轮另建专题，保留上一轮的设计背景；专题页内部维护该轮最新确认稿。

正文顶部列出本轮涉及的原型入口。原型入口指向该能力当前可评审版本，历史 PRD 不能据此声称旧画面仍被保留。是否已实现，以目标代码或运行证据核实。

## 默认内容

1. 原型入口：按端和能力列出可直接打开的页面。
2. 问题与目标：谁在什么场景遇到什么问题，本轮希望改变什么。
3. 本轮内容：列出涉及端与功能。
4. 关键场景与规则：写清触发条件、用户可见反馈、状态变化，以及权限、校验和重要异常。

未确认的产品答案标为“产品待定”。区分已确认设计、已核实事实和推断。仅在有明确产品目标时写性能或安全指标；接口字段、库表和实现方案不作为 PRD 的必填部分。

## 元数据示例

```yaml
---
kind: requirement
title: "示例需求标题"
date: 2026-09-24
tags: ["管理端", "小程序"]
prototypeEntries:
  - title: "示例管理端入口"
    path: /prototypes/admin/example/index.html
    surface: admin
    capability: example
---
```

`prototypeEntries` 只登记真实存在、可访问的入口。没有原型时可暂不填写，并在正文说明当前评审材料。站点会从元数据生成需求和原型目录。
